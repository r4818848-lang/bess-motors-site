# BESS MOTORS: выпуск PR #24

Этот документ описывает, что попадёт в production при выкладке ветки PR #24, что останется выключенным, и как откатить каждую часть. Выкладка, merge и SQL на боевой Supabase этим PR не выполняются.

## Что включится сразу после deploy

Эти части не спрятаны за флагами Smart Scheduler.

- Часы приезда клиента: понедельник–пятница 09:00–17:30, суббота 09:00–13:30, воскресенье закрыто, шаг 30 минут. Сервис по-прежнему работает до 18:00 и 14:00. Приезд в 17:30 не назначает механику работу после закрытия: остаток переносится на следующий открытый день.
- Сохранение заявок с сайта и защита от повторного POST. Одна открытая заявка в течение 24 часов. Закрытая заявка или заявка старше суток не блокирует новую, даже если браузер прислал прежний `clientRequestId`.
- Отдельная доставка Telegram каждому `adminChatId`, claim token и аренда 2 минуты. Успех одного чата не закрывает остальные. Ошибка пишется в `lastError`.
- Cron `GET /api/telegram/cron/lead-notices` каждые 5 минут. Он повторяет `pending` и просроченный `sending` младше 24 часов. Тот же вызов остаётся в конце `/api/telegram/cron/appointment-reminders`, если повтор заявок не выключен отдельно.
- Уведомления новым клиентам не отключаются. На preview и при `REMINDER_DELIVERY=disabled` отправка cron не идёт. `LEAD_NOTICE_DELIVERY=disabled` останавливает только повтор заявок: напоминания о записи и немедленное сообщение по новой заявке продолжаются.

Расписание `*/5` уже используется боевым cron напоминаний. На тарифе Vercel, который не принимает такой интервал, отклонился бы и существующий cron. Отдельный ежедневный запасной запуск на production не включался.

## Что останется выключенным

Пока владелец явно не задаст переменную, эти функции не работают.

| Переменная | Значение по умолчанию | Эффект |
|---|---|---|
| `SMART_WORK_SCHEDULER` | не задана | Планировщик и его запись закрыты |
| `SCHEDULER_UNIFIED_CALENDAR` | не задана | Общий режим записи не требуется. На Vercel переменная игнорируется |
| `SCHEDULER_TEST_WRITES` | не задана | Тестовая запись в PostgreSQL закрыта на preview и production всегда |
| `SCHEDULER_READ_ONLY_PILOT` | не задана | `/telegram/scheduler` отвечает 404 |
| SQL `unified_calendar` | `false` в черновике | Боевая запись CRM не переключается |

`productionCrmUrl()` остаётся пустым. `schedulerCrmWritesEnabled()` и `schedulerUnifiedCalendarWired()` всегда `false`.

## Что требует SQL

Файлы `supabase/drafts/smart-scheduler.sql`, `smart-scheduler-rollback.sql`, `smart-scheduler-switch.md` и `smart-scheduler-pilot.md` на боевую базу не применялись. Read-only календарь читает уже существующий CRM и новые таблицы не требует. Запись планировщика без этого SQL невозможна.

## Переменные окружения

Уже используются сайтом и ботом, этот PR их не меняет:

- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHAT_ID`
- `TELEGRAM_ADMIN_CHAT_IDS`
- `CRON_SECRET`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY` — только на сервере

Для повтора заявок:

- `REMINDER_DELIVERY` — пусто или `live` на production разрешает отправку cron. `disabled` останавливает все cron-рассылки, включая напоминания. Preview не отправляет в любом случае.
- `LEAD_NOTICE_DELIVERY` — не задавать при обычном запуске. `disabled` останавливает только повтор заявок и не трогает остальные cron.

Проверка наличия без значений: `npm run check:release-env`. Скрипт печатает `present` или `missing`. Для флагов из короткого списка печатает само значение. Секреты не печатает. Запуск в этой среде не видит переменные Vercel.

Перед публикацией владелец сверяет в Vercel → проект `bess-motors-site` → Production:

- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_ADMIN_CHAT_IDS`, `CRON_SECRET` заданы.
- `REMINDER_DELIVERY` пустой или `live`.
- `LEAD_NOTICE_DELIVERY` не задан.
- `SMART_WORK_SCHEDULER`, `SCHEDULER_UNIFIED_CALENDAR`, `SCHEDULER_TEST_WRITES`, `SCHEDULER_READ_ONLY_PILOT` не заданы.

Значения в чат и в Git не копировать.

Для будущего просмотра календаря, без записи:

- `SCHEDULER_READ_ONLY_PILOT=production-readonly`
- `SCHEDULER_CRM_SOURCE=cloud`
- `SMART_WORK_SCHEDULER`, `SCHEDULER_UNIFIED_CALENDAR` и `SCHEDULER_TEST_WRITES` не задавать

Кнопка Mini App должна открывать `https://<хост>/telegram/scheduler`. Подпись `initData` проверяется сервером. Без подписи доска отвечает 401. Если CRM недоступна, ответ 503, а не пустой день.

## Как открыть только просмотр

1. Убедиться, что три флага записи не заданы.
2. Задать `SCHEDULER_READ_ONLY_PILOT=production-readonly` и `SCHEDULER_CRM_SOURCE=cloud` на production.
3. В BotFather указать Mini App URL `/telegram/scheduler`.
4. Открыть с телефона владельца. Ожидаются колонки «Сергей» и «Механик 2», реальные записи и отказ на создание, перенос и отмену.
5. Чтобы закрыть просмотр, удалить `SCHEDULER_READ_ONLY_PILOT`. Запись клиентов и сайт при этом не меняются.

## Защита уведомлений

- Событие одно: `lead-notice:<leadId>`.
- На каждый чат: статус, попытки, `claimToken`, `leaseUntil`, `messageId`, `sentAt`, `lastError`.
- Резерв пишется в CRM до `sendMessage`. Повтор формы не резервирует событие заново.
- Старый токен не завершает новую попытку.
- Заявка со статусом `sent` без построчных получателей считается уже доставленной и не отправляется пакетом.
- Заявка старше 24 часов не повторяется.
- Если Telegram принял сообщение, а процесс оборвался до записи `sent`, повтор возможен. Exactly-once сервис не обещает.

## Какой Vercel-проект боевой

9 ноября 2026, около 17:22 по Европе/Варшава, `https://www.bess-motors.com` и `https://bess-motors-site.vercel.app` отдали один и тот же `etag`. `bess-motors.vercel.app` и `bess-motors-site-5dyd.vercel.app` отдали другие. Домен обслуживает проект **bess-motors-site**.

При push в `main` Vercel сам создаёт Production у трёх проектов: `bess-motors-site`, `bess-motors` и `bess-motors-site-5dyd`. Так произошло для `87eb23b` 8 ноября 2026 в 16:46 по Европе/Варшава. GitHub Action `Deploy to Vercel` на этих push завершается ошибкой `vercel-token` не задан и сайт не публикует.

Публикация — это merge в `main`. Отдельного шага «задеплоить позже» у текущего подключения нет. Два лишних проекта тоже получат этот код. Перед merge владелец проверяет, что cron и боевые ключи CRM есть только у `bess-motors-site`. Иначе три расписания будут смотреть в одну CRM. Аренда `cronHoldUntil` не даёт им отправить одно и то же дважды, только если все три смотрят в один документ.

## Резервная копия

SQL этому релизу не нужен. Новые поля уведомления пишутся в существующий документ CRM при новой заявке и при повторе незакрытой заявки младше суток. Клиенты, автомобили и заказ-наряды код не удаляет.

Перед merge владелец снимает копию в панели Supabase: Database → Backups, либо `pg_dump` со своей машины в файл вне Git. Этот репозиторий к боевой базе не подключается.

Проверка восстановления, на отдельной базе:

1. Поднять пустой проект Supabase или локальный PostgreSQL.
2. Восстановить туда файл копии.
3. Не подставлять эту базу в Vercel production.
4. Сверить число клиентов, автомобилей, заявок, записей и заказ-нарядов с цифрами, снятыми до публикации.
5. Убедиться, что сайт production по-прежнему открывает прежнюю базу.

## Проверка старых заявок без записи

`tsx scripts/audit-lead-notices.ts leads.json` читает локальный файл и печатает только счётчики. К Supabase не подключается: если в окружении есть адрес `supabase.co`, скрипт завершается с кодом 3 и ничего не читает.

Заявка `sent` без построчных получателей не отправляется снова. Заявка старше 24 часов не отправляется, даже если статус `pending` или `sending`. Повтор возможен только у незакрытой заявки младше суток. Это тот же предел, который уже стоит в боевом cron напоминаний.

## Откат

- Сайт: в Vercel у проекта `bess-motors-site` выбрать предыдущий production deployment и Promote. Клиенты остаются в Supabase. Обратный SQL не нужен.
- Повтор заявок, не трогая напоминания: `LEAD_NOTICE_DELIVERY=disabled` только в `bess-motors-site`, затем Redeploy текущего production. Новая заявка с сайта по-прежнему отправляет сообщение сразу. Уже записанные заявки остаются.
- Все cron сразу: `REMINDER_DELIVERY=disabled`. Это останавливает и напоминания о записи, утренний отчёт и остальные рассылки. Для одной проблемы с заявками этот шаг не использовать.
- Read-only: удалить `SCHEDULER_READ_ONLY_PILOT`. Сайт и запись клиентов не меняются.
- Запись планировщика этим выпуском не включается. Если SQL применят позже, обратный файл — `supabase/drafts/smart-scheduler-rollback.sql`. Он не трогает `crm_store` и `appointments`.
- После отката открыть сайт, существующий календарь и одну известную запись. Число клиентов не должно уменьшиться.

## Первый запуск, отдельно от read-only

1. Копия Supabase и сверка на отдельной базе.
2. Переменные production, без копирования значений в чат.
3. Флаги записи Smart Scheduler не заданы.
4. `audit-lead-notices` на выгрузке: старые `sent` не в `sends`. Если `sends` больше незакрытых заявок последних суток, до merge задать в `bess-motors-site` значение `LEAD_NOTICE_DELIVERY=disabled` и сделать Redeploy после сохранения переменной. Новые заявки при этом всё равно отправляются сразу.
5. Merge в `main` только после разрешения владельца.
6. Открыть `https://www.bess-motors.com`.
7. Одна служебная заявка сотрудника, не от имени клиента.
8. В Telegram каждому администратору одно сообщение. Второго такого же нет.
9. На сайте пятница 17:30 доступна, 18:00 нет.
10. Суббота 13:30 доступна, 14:00 нет.
11. Существующий календарь открывает прежние записи.
12. При повторе старых заявок поставить `LEAD_NOTICE_DELIVERY=disabled`. При поломке сайта — Promote предыдущего deployment.

Read-only `/telegram/scheduler` включается следующим, отдельным шагом по разделу «Как открыть только просмотр». В первый релиз его не смешивать.

## Что этот выпуск не делает

- Не меняет клиентов, автомобили, VIN, телефоны, заказ-наряды и историю.
- Не назначает реальные работы на mech-2: личность не подтверждена.
- Не подтверждает допуск UDT. Подъёмники в production-настройках остаются на обслуживании и без автоматической брони.
- Не открывает запись Smart Scheduler.
